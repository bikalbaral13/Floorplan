name: Author the standard plan JSON in image pixels
category: Floorplan Tracer
when: Measured walls, columns, classified openings and a fixture list exist and it is time to emit the canvas JSON (schemaVersion 1: settings · nodes · segments · spaces · layers · imageUnderlay).
tools: [Bash]
requires: [calibrate-scale-from-printed-dimensions, measure-wall-bands-from-pixels, read-openings-and-fixtures-by-zoom]
---

Write ONE build script (`build.mjs`) whose constants are image-pixel coordinates and whose output is the standard plan format. Regenerating the file from the script after every correction is what keeps 170 nodes consistent; editing the JSON by hand is how you break a junction.

**Frame.** `OX = -W/2, OY = -H/2`; every emitted node is `(px + OX, py + OY)` rounded to 2 dp. `settings = { library_path: <R2 base>/library, units: "m", northbearing: 0, pixelsPerMeter: <calibrated> }` plus a `source` block recording the image name, its pixel size, px/ft and the world origin so the next person can re-derive the frame. `imageUnderlay = { id, src, x: OX, y: OY, width: W, height: H, opacity: 0.55, scale: 1, locked: true, layerId: "image" }` — `src` is the data URL in the self-contained file, or `<library_path>/Images/<file>` in the light one.

**Nodes.** One node per distinct exact position, via a `N(x, y)` memo. Reuse the same named constant for every wall on a line (`xR = 840.5`, `yMid = 599.5`) — the format merges nodes only on identical coordinates. **At a 90° bend both walls end ON the shared centreline node and nowhere else** — no stub carried past the junction to the outer face. The mitred join fills the outer corner by itself; a stub there is a third segment meeting at the corner, which the mitre then draws as a visible notch. The same holds at a T (a horizontal ending on a vertical that runs through): stop at the centreline. The ONE case that keeps a short piece is an opening at a junction, and it is a rule, not a cosmetic choice: **a door, window or opening piece is not a wall and only connects through wall.** Collinear (in series) with a wall it already sits between wall pieces and nothing extra is needed. But its end must never land on a PERPENDICULAR wall's centreline node — at a T or a corner insert a short wall segment of the opening's own thickness between the junction node and the opening's jamb, so the mitre joins wall to wall and the opening hangs off that (Bedroom-1 door → Toilet-1 wall: `wall(480, yMid, xB1R, yMid)`; main door → living/shaft wall: `wall(xR, 592, xR, yMid)`; kitchen–utility opening → kitchen-right wall: `wall(768.5, yBot, xKR, yBot)`; the balcony's open side, whose BOTH ends meet perpendicular walls: `wall(xPar, yDuctBot, xPar, 410, 10); opening(xPar, 410, xPar, 592, 10, …); wall(xPar, 592, xPar, yMid, 10)`). Without the stub the opening band stops short of the wall with a wedge at the junction — the black gap the user circled on Windsor Park's balcony.

**Walls** are `segmentType: "line"` bands, never `"wall"`: `{ layer: "wall", thickness: <px>, color, mode: "fill", method: "center", bufferStyle: "flat", hatch: true, hatchStyle: "diagonal", hatchSpacing: 6, lineStyle: "solid" }` carrying one Wall attachment `{ objectId: "wall-with-math", objectPath: "Objects/Architectural/wall.json", params: { thickness: <m>, height: 2.7, mode: "Buffered", hatch: true, fitMode: "Fill segment" }, t: 0.5 }`. Thickness is per wall piece, from the measurement, in px on the segment and metres on the object. Parapets, duct outlines and open shaft edges are the same band with `hatch: false`, thickness 2–4 px, height ~1 m.

**Columns are objects, not thicker walls.** A dark block projecting past a wall's face has a different centreline from the wall; thickening the wall piece would push its inner face into the room. Run the wall line straight through at its own thickness and put a node-hosted `Objects/Structural/column.json` on top at the block's true centre: `{ shape: "Rectangular", length: m(x1−x0), breadth: m(y1−y0), height: 3, rotation: 0 }` (its 2D symbol is the section with centre axes). Values past the slider range (`length` > 2) still evaluate.

**Openings are pre-cut**, not left for the app to cut: split the wall run at the measured light-run edges into `wall · opening · wall` pieces sharing nodes. The opening piece keeps every wall field, adds `isObjectOpening: true`, goes on layer `"door"` / `"window"`, and carries TWO attachments: the Wall object (so 3D keeps a spandrel) and the Door / Window object. Door params: `{ width: <gap m>, leaves, hinge, swing, openAngle: 90, fitMode: "Fill segment", frameDepth: <wall m>, lintelHeight: 2.1 }`. Window: `{ width, fitMode: "Fill wall", sillHeight, lintelHeight: 2.1, wallDepth: <wall m>, panes, operation, showFrame: true }`. Because the piece is exactly the gap, `t: 0.5` and "Fill" modes are always right. Give each a `label` ("Bedroom-2 door", "Balcony sliding door") — it is how the user finds it in Properties.

**Door hinge / swing are decided by the door object's own maths, relative to the segment's start→end direction `u`** (read from `door.json`, verified on five doors): `hinge: "right"` puts the pivot at the END node, `"left"` at the START node; `swing: "left"` opens toward the side `(−uy, ux)` — for a segment authored left→right that is DOWN the screen (+y), for one authored top→bottom it is LEFT (−x) — and `"right"` toward the opposite side. So a door in a horizontal wall that swings up into the room above is `swing: "right"`. The attachment's `flip` flag is read only by the editor's legacy non-parametric door symbol; parametric doors ignore it, so it cannot fix a wrong side — change `swing`.

**Open boundaries — a wall gap with no leaf** (kitchen → living, kitchen → utility) are NOT thin dashed lines. A thin line meeting a full-thickness band makes the mitre taper both wall ends to a point (the wedge in the kitchen entrance on the first Windsor pass). Author the gap as a pre-cut piece of the ADJACENT wall's thickness — `isObjectOpening: true`, layer `"opening"`, the segment keeps `thickness`, `mode: "fill"` and `bufferStyle` — carrying ONLY `Objects/Architectural/opening.json` `{ width: <gap m>, fitMode: "Fill segment", thickness: <wall m>, lintelHeight: 2.1, dashLength: 0.12, dashGap: 0.08 }` and NO Wall attachment. An opening is vacant: nothing may stand in it in 2D or 3D. The segment's thickness is still what the mitre uses at both ends (so the neighbouring wall ends stay square instead of tapering to a point) and what the space label insets by; `isObjectOpening` makes the canvas draw the band as a gap; the object draws one dotted line along the centreline across the gap and nothing else — no jambs, no lintel, no sill wall — and it has no 3D render node. A door / window piece is different: it KEEPS the Wall attachment, because the editor carves that wall into the spandrel over the leaf; an opening piece must not, or the 3D view fills the gap. `thickness` should equal the host piece's segment thickness (reported back as the "Thickness (m)" metric; `wallDepth` is the pre-2026-09 name and is still honoured). A balcony's open side is the same vacant opening between two short full-height wall returns — no parapet. Where the two neighbours differ in thickness use the thickness of the wall the gap actually interrupts. A balcony or verandah OPEN SIDE (drawn as a thin line) is the same vacant opening between the two wall returns — not a 4 px hatch-less wall, and not a parapet. A thin dashed `mode: "line"` segment remains right only for a space divider that is not a wall gap at all (the edge of a niche or an alcove).

**Thin drawn lines that are not walls** (a shower screen, the edge of a duct) can go in as `mode: "line"` segments of thickness 1.5 on their own `ledge` layer. But NEVER trace an open polyline that touches a wall from the outside — the three-sided chajja boxes outside windows, for instance. On import the auto-room detector closes every such polyline against the wall and produces a 0.4 m² `Space00N` sliver that the user then has to delete. Lines fully inside a manual space are fine (the manual space suppresses the auto twin).

**Spaces** are explicit, one per room, and their ring sits on the wall CENTRELINES — the shared wall nodes, never the inner faces. That is the editor's own convention (the Space tool clicks wall nodes; auto-rooms come from the wall graph), and the editor's label — with "Subtract segment for Space" on, which is the default — insets each ring edge to the wall face by itself: per edge, the LARGEST half-thickness of any band collinear with the edge whose midpoint projects onto it, floored at half the current wall style (10 px → 5 px; that floor is also what an edge with no band gets, e.g. a duct's thin edge line). A ring authored on the inner faces is therefore inset TWICE and reads 4–10 inches small — the first Windsor pass showed 20' 2" × 10' 2" for a 20'6" × 11' living room for exactly this reason. Because the rule takes the max per edge, a run of walls of mixed thickness along one edge insets by the thickest; author collinear pieces at one thickness where the render allows (Windsor's 19 px shaft-top piece is authored at 17 with the rest of that line). The floor is the user's own drawing setting, not a constant (it was ≈0 in the Windsor session, not 5), so a printed room must never have an edge with NO band under it — a duct's thin edge line, an alcove mouth. Give such an edge a real thin band (a 10 px low kerb wall, height 0.6, hatch off) so its inset is its own half-thickness whatever the floor is; keep only bands of ≥ 10 px on printed rooms for the same reason. Replay the rule in the build script over the emitted rings and print the predicted label L×B in feet-inches beside the printed value; it must be 0.000 ft off for every printed room, and the replay must warn on any printed-room edge that found no band. A rectangle `[x0, y0, x1, y1]` on the four centreline constants, or an explicit ring for an L: `{ layer: "space", label, showLabel: true, roomType: "room", fill, stroke, fillOpacity, region? }` with the Room attachment `{ objectId: "room-with-math", objectPath: "Objects/Architectural/room.json", params: { color }, t: 0 }`. Toilets get `region: "Toilet"` and a blue fill, balconies `region: "Balcony"`, ducts / shafts / niches `roomType: "area"`. A manual space suppresses the auto-detected twin whose centroid is within 10 px, so labels and colours survive import. Where a ring corner needs a wall node that does not exist yet (Bedroom-2's bottom-left is mid-wall), split that wall at the constant so the node is shared. The Room object's own Area metric is the centreline area (bigger than the print by the half-bands); the editor's "Area: … ft²" caption is the inset net area and is the one that matches the print.

**Node-hosted objects** (all furniture and fixtures) use the editor's own placeObject shape: a zero-length marker segment `{ fromNodeId: n, toNodeId: n, layer: <kind>, thickness: 0.5, mode: "line", segmentType: "wall" }`, the attachment on that node `{ objectId: "<kind>-with-math", objectPath: "Objects/<Category>/<kind>.json", params: { rotation, anchorDir: "Center", fitMode: "Off", ...dims in m }, t: 0 }`, and `graphAttrs.nodes["<segId>:end|<segId>:start"] = { "node-type": "object" }` (key parts sorted). Nodes with attachments go on layer `"0"`; give each object kind its own layer so the user can hide all wardrobes at once. Read each object's parameter names from its `input-props` node before using it (`length/width` for bed, table, toilet…; `width/depth` for wardrobe, cabinet, chair; `length/depth` for sofa) and clamp to the slider range where the file enforces one (`dressing-table.length ≤ 1.8`, `armchair.length ≥ 0.5`).

**Layers**: the four seeds (`0`, `image`, `map`, `dimension`) then `wall`, `door`, `window`, `space`, then one per object kind, `order` ascending.

Print, at the end of the script: node/segment/space/object counts and every space's area in m² beside its printed L×B (Δ %). Read those numbers before you look at any picture.
